# ADR-7：引入 LangChain 的边界与默认实现选择

| 项 | 值 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-11-15 |
| 影响范围 | `src/app/client/`、`src/app/core/config.py` |
| 相关决策 | 分层与依赖方向、统一错误契约 |

> 编号沿用项目既有 ADR 序列。

---

## 1. 背景

v0.1 的 `src/app/client/llm.py` 已经实现了一套完整的 LLM 客户端抽象：

| 已有能力 | 实现方式 |
|---|---|
| 依赖倒置 | `LLMClient` Protocol 由业务层定义，SDK 反向实现 |
| 结果对象 | `ChatResult` 携带 `text` / `usage` / `finish_reason` / `latency_ms` / `tool_calls` |
| 异常语义 | 六类 `LLMError` 子类，SDK 异常在边界处统一翻译 |
| 多供应商 | `OpenAICompatClient` 通过 `base_url` + `model` 覆盖所有 OpenAI 兼容端点 |
| 测试替身 | `FakeClient` 支持脚本化返回，Function Calling 链路可离线验证 |

与此同时，后续的检索增强与多步 Agent 需要的能力在这套抽象之外：Prompt 模板、
结构化输出解析、链式组合、回调与可观测。这些正是 LangChain 已经提供、而手写实现
尚未覆盖的部分。

问题因此不是「要不要用 LangChain」，而是「**放在哪一层、以什么身份存在**」。

---

## 2. 决策

**保留 `OpenAICompatClient` 作为默认实现，LangChain 以「可切换的第二实现」接入。**

具体形态：

1. 新增 `src/app/client/lc_client.py`，实现与手写版**完全相同**的 `LLMClient` 协议
   （`achat` / `astream`），返回值同为 `ChatResult`。
2. `core/config.py` 增加 `llm_backend: Literal["openai", "langchain"] = "openai"`。
3. `build_client()` 按该配置分派，业务层不感知差异。
4. 分层规则收紧：**`service/` 与 `router/` 不得 import 任何 LLM 框架或 SDK**，
   适配代码只允许出现在 `client/`（以及后续的 `rag/`、`agent/`）。

---

## 3. 理由

| 理由 | 说明 | 代价 |
|---|---|---|
| 异常语义可控 | 现有六类异常是业务层 `except LLMError` 的唯一依据；框架的异常族无法保证与之一一对应，替换后错误分类会变粗 | 需要维护一层异常翻译，且需实测框架在各类失败下抛什么 |
| 抽象层浅，便于定位 | 手写路径只有「一层 SDK 调用」；框架路径多出 Runnable 调度、消息转换、回调三层，排查慢请求时链路更长 | 双实现意味着两条排障路径 |
| 版本漂移风险隔离 | 框架处于快速演进期，大版本间 API 与字段名均有变动；默认走手写路径可让主干不受影响 | 需要锁定版本并在升级时重跑对比 |
| 后续能力可直接复用 | 检索、Agent、可观测都建立在框架的组合语义上，届时不必二次造轮子 | 引入的依赖体积与心智负担 |

**决定性因素**：本项目的第一诉求是「可解释、可排障」，而不是「功能最多」。
在排查「为什么慢」时，一层调用比四层抽象更容易给出确定答案。

---

## 4. 后果

### 正面

- 主干行为不变，既有测试与压测结论继续有效。
- 新增能力可以在第二实现上验证成熟后再决定是否上提。
- 两套实现并存，形成天然的对照实验：同一输入下回答是否一致、成本是否一致。

### 负面

- 维护两套实现的成本，主要体现在适配层的字段映射上。
- 需要额外的对比脚本，否则「双实现」会退化成「一份没人用的代码」。

### 触发重新评估的条件

出现以下任一情况时，本决策需要重新审视：

1. 第二实现在连续两个版本周期内未被任何功能使用；
2. 框架的异常与用量字段在同一大版本内发生破坏性变更；
3. 对比结果显示两套实现在关键指标上无差异，且手写版维护成本显著更高。

---

## 5. 实施约束（可检查）

这些约束用于防止「决策写在文档里、代码里慢慢失效」：

| 约束 | 检查方式 | 期望结果 |
|---|---|---|
| 业务层不依赖框架 | `grep -rn "langchain" src/app/service src/app/router` | 无输出 |
| 第二实现符合协议 | `isinstance(LangChainClient(settings), LLMClient)` | `True` |
| 切换后端不改变对外契约 | 切换 `APP_LLM_BACKEND` 后请求 `/chat`，比对响应体结构 | `{code, msg, data, request_id}` 一致 |
| 字段映射不静默失效 | 单元测试断言 `usage.prompt_tokens > 0`、`tool_calls` 为列表 | 全部通过 |

其中最后一条针对的是最容易漏掉的失败模式：映射写错时不会抛异常，
只会让用量恒为 0、工具调用恒为空。

---

## 6. 备选方案

| 方案 | 做法 | 优点 | 否决原因 |
|---|---|---|---|
| A. 全量替换 | 删除手写客户端，统一走框架 | 代码量减少，只维护一条路径 | 失去对照基线；异常语义与排障深度不可控；既有测试需大规模重写 |
| B. 不引入 | 继续手写，按需自行实现模板与解析 | 依赖最少，完全可控 | 检索与 Agent 阶段的组合、回调、可观测需重复造轮子，成本高于收益 |
| C. 双实现（采纳） | 手写为默认，框架为可切换的第二实现 | 保留对照与退路，可按功能逐步迁移 | 维护成本增加，需要对比机制兜底 |

---

## 7. 未决问题

1. **流式用量**：框架在流式返回中是否稳定提供 usage，需实测确认；若不可得，
   需要在文档中明确「流式路径的成本统计精度低于非流式」。
2. **异常覆盖度**：框架的异常族与现有六类之间的映射表尚未建立，
   需要逐类触发失败并记录实际异常类型后再定稿。
3. **版本锁定策略**：依赖是否跟随主版本升级，取决于对比脚本能否稳定检出行为差异。
4. ~~**采样参数的字段改名**~~ **已定论（2026-11-15 实测）**：把 `max_tokens` 交给框架后，
   请求体里出现的是 `max_completion_tokens`，而 OpenAI 兼容端点不认该字段 ——
   传 60 实际生成 143，参数被静默忽略。适配层已改为把它并入 `extra_body`，
   实测 60 → 60 生效。附带发现：框架默认**不关闭思考模式**，同一问题思考开 130 完成
   token、关 50，正文反而更短；适配层已显式传 `thinking.type=disabled`。
   两处修复后，两后端在 5 条金标上的 `prompt_tokens` 完全一致，一致率 5/5。
