# 首张压测表（2026-11-10）

> 这是 CodeLoom v0.1 的第一份压测记录。目的不是刷数字，而是回答三个问题：
> ① 框架本身的开销有多大；② 端到端延迟里上游占多少；③ 流式是不是真的把「感知延迟」降下来了。

---

## 1. 环境与口径

| 项 | 值 |
|---|---|
| 服务 | Windows 本机，`uvicorn --workers 1`，端口 8001 |
| 模型 | `deepseek-flash`，`max_tokens=100` |
| 压测器 | **同机** Python asyncio + httpx，关环并发（N worker = N 在途） |
| 限流 | `APP_RATE_LIMIT=100000`（关闭，避免干扰吞吐测量） |
| 日志 | `APP_LOG_LEVEL=WARNING`（避免日志 IO 成为瓶颈） |
| 时间 | 2026-11-10 20:52（UTC+8） |
| 代码 | v0.1 工作区（压测时为未提交状态） |

复跑命令见 [`benchmark/README.md`](README.md)；原始 JSON 在 `benchmark/results/`（不入库）。

## 3. 三个结论

### 3.1 我们的开销只占端到端 1~2%

- `/healthz` 的 P50 是 **14 ms**（框架 + 序列化 + 回环）
- `/chat` 的 P50 是 **1304 ms**
- `/stream` 的 TTFB P50 是 **609 ms**

按 TTFB 算：14 / 609 ≈ **2.3%**；按非流式总时长算：14 / 1304 ≈ **1.1%**。
剩下的都是上游生成与网络 —— 这个比例是「这项目该不该优化」的直接依据：**优化我们的代码不会让聊天变快**。

### 3.2 流式把「感知延迟」砍掉一半

| 指标 | 非流式 | 流式 |
|---|---:|---:|
| 用户看到第一个字 | 1304 ms（要等全量） | **609 ms（首个 delta）** |
| 看完全部内容 | 1304 ms | 1091 ms |

流式的总时长没有优势（甚至略短是因为生成长度不同，不能直接比），
真正价值是**首字延迟减半** —— 这是产品指标，不是服务器指标。

### 3.3 `/chat` 的 RPS 完全由上游决定，我们这里没有排队

```
RPS ≈ 并发 / 单请求延迟
1.5 ≈ 2 / 1.304      （实测 1.5）
```

这个等式成立，说明服务端**没有积压**：来两个请求就并行两个，谁也没等谁。
如果 RPS 明显低于这个值，才说明有排队（连接池、GIL、SQLite 锁、限流）。

同理 stream：`1.8 ≈ 2 / 1.091`。

## 4. 瓶颈判断

| 层 | 证据 | 判断 |
|---|---|---|
| 框架 | probe 928 RPS，P99 104ms | 不是瓶颈；且这是**同机 Python 客户端**测出的下限（客户端与服务端抢 CPU） |
| 上游 | chat 延迟 ≈ 1.3s，token 449+68 | **主要瓶颈**；加并发只会线性提高 RPS，直到上游限流/配额 |
| 存储 | chat 每轮 2 次写（user + assistant），未出现 P99 尖刺 | 单进程下不是瓶颈；`workers>1` 才会暴露 |
| 客户端 | probe P99/P50 ≈ 7 倍 | 可能是 Windows 定时器精度（~15ms）与 GC，不是服务端排队 |

---

## 5. 口径与局限（必须和数字一起说）

1. **样本少**：chat / stream 各 10 发，`P99` 实际等于最大值，不要当成稳定分位数。
2. **同机压测**：客户端与服务端共享 CPU，probe 的 928 RPS 是**下限**，不是服务上限。
3. **单进程**：`--workers 1`（SQLite 锁与限流器都是进程内状态），数字代表单机能力。
4. **Windows**：定时器精度约 15ms，亚 10ms 的差异不可信。
5. **未做并发扫描**：只测了 c=2，没有找饱和点；也没做 429 压测（限流被关掉了）。
6. **生成长度不同**：chat 与 stream 的回答长度不完全一致，总时长不能严格横向比较。

## 6. 下一步能补什么

| 项 | 目的 | 怎么做 |
|---|---|---|
| 并发扫描 | 找 RPS 的拐点 | `chat --concurrency 2/5/10`，看 RPS 是否还满足 `c/延迟` |
| 429 压测 | 验证限流与退避 | 用默认 `APP_RATE_LIMIT=30`，`--requests 40`，看 `retry_after_seen` |
| 资源采样 | 证明瓶颈不在我们 | 压测时并行 `pidstat -p <pid> 1`（WSL/Linux）或任务管理器（Windows） |
| wrk2 复核 | 拿到 probe 的真实上限 | `wrk2 -t4 -c200 -d30s -R2000 http://127.0.0.1:8001/healthz` |
